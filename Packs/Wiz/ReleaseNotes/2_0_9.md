
#### Integrations

##### Wiz

- Migrated Issue notes to the Wiz Comments API ahead of the retirement of the Issue Notes API. ***wiz-set-issue-note***, ***wiz-clear-issue-note***, and the note arguments of ***wiz-reject-issue***, ***wiz-resolve-issue***, and ***wiz-reopen-issue*** now create and delete Issue comments; incoming mirroring reads Issue comments.
- **Action required:** the Wiz service account used by the integration needs the `write:comments` scope to add notes (commands and outgoing mirroring), the `read:comments` scope for incoming mirroring, and both scopes plus `admin:comments` for ***wiz-clear-issue-note*** to delete other authors' comments. `admin:comments` does not replace the read/write scopes. Review the service account's permissions before upgrading. The legacy `write:issue_comments` and `write:threat_issue_comments` scopes do not grant access to Issue comments.
- Issue notes are no longer included in fetched incident data or in the output of ***wiz-get-issue*** and ***wiz-get-issues***. Comments are requested only by ***wiz-clear-issue-note*** and incoming mirroring.
- ***wiz-clear-issue-note*** and incoming mirroring cover Issue comments only. Notes added through the legacy Issue Notes API that do not appear as comments in Wiz are not cleared or mirrored.
- If the service account lacks the `read:comments` scope, incoming mirroring still updates Issue fields such as status and due date, and skips comments.
- If the service account lacks the `write:comments` scope, ***wiz-resolve-issue***, ***wiz-reject-issue***, and ***wiz-reopen-issue*** still update the Issue status and return a warning that the note could not be added.
- On tenants that require a note when rejecting Issues, ***wiz-reject-issue*** and mirrored rejections keep working until the Issue Notes API is retired. After that, disable **Require note on rejection** in the Wiz Issue settings or reject the Issue in Wiz.

##### WizDefend

- Migrated threat comments to the Wiz Comments API. ***wiz-defend-set-threat-comment***, ***wiz-defend-clear-threat-comments***, and the note arguments of ***wiz-defend-resolve-threat*** and ***wiz-defend-reopen-threat*** now use Issue comments.
- **Action required:** the service account needs `write:comments` to add comments, and `read:comments` and `write:comments` plus `admin:comments` for ***wiz-defend-clear-threat-comments*** to delete other authors' comments. `admin:comments` does not replace the read/write scopes. The legacy `write:threat_issue_comments` scope does not grant access to Issue comments.
- Threat notes are no longer included in fetched incidents or in the output of ***wiz-defend-get-threat*** and ***wiz-defend-get-threats***.
- ***wiz-defend-clear-threat-comments*** clears Issue comments only. Notes added through the legacy Issue Notes API that do not appear as comments in Wiz are not cleared.
- If the service account lacks the `write:comments` scope, ***wiz-defend-resolve-threat*** and ***wiz-defend-reopen-threat*** still update the threat status and return a warning that the note could not be added.

#### Mappers

##### WizDefend Mapper

- Removed the **Wiz Issue Note** mapping, which relied on the retired Issue Notes field.
