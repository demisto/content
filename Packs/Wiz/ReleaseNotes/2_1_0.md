
#### Integrations

##### Wiz

- Updated the Issue notes to use the Wiz Comments API ahead of the retirement of the Issue Notes API. ***wiz-set-issue-note***, ***wiz-clear-issue-note***, and the note arguments of ***wiz-reject-issue***, ***wiz-resolve-issue***, and ***wiz-reopen-issue*** now create and delete Issue comments; incoming mirroring reads Issue comments.
- Updated the required service account scopes: *write:comments* to add notes (commands and outgoing mirroring), *read:comments* for incoming mirroring, and both scopes plus *admin:comments* for ***wiz-clear-issue-note*** to delete other authors' comments. *admin:comments* does not replace the read/write scopes. The legacy *write:issue_comments* and *write:threat_issue_comments* scopes do not grant access to Issue comments.
- Updated the ***wiz-get-issue*** and ***wiz-get-issues*** commands and the fetched incident data to no longer include Issue notes. Comments are requested only by ***wiz-clear-issue-note*** and incoming mirroring.
- Updated the ***wiz-clear-issue-note*** command and incoming mirroring to cover Issue comments only. Notes added through the legacy Issue Notes API that do not appear as comments in Wiz are not cleared or mirrored.
- Improved implementation of incoming mirroring to keep updating Issue fields, such as status and due date, and skip comments when the service account lacks the *read:comments* scope.
- Improved implementation of the ***wiz-resolve-issue***, ***wiz-reject-issue***, and ***wiz-reopen-issue*** commands to update the Issue status and return a warning when the note cannot be added, for example when the service account lacks the *write:comments* scope.
- Fixed an issue where status comments written by outgoing mirroring were mirrored back into the incident War Room.
- Updated the ***wiz-reject-issue*** command and mirrored rejections to keep working on tenants that require a note when rejecting Issues until the Issue Notes API is retired. After that, disable **Require note on rejection** in the Wiz Issue settings or reject the Issue in Wiz.

##### WizDefend

- Updated the threat comments to use the Wiz Comments API. ***wiz-defend-set-threat-comment***, ***wiz-defend-clear-threat-comments***, and the note arguments of ***wiz-defend-resolve-threat*** and ***wiz-defend-reopen-threat*** now use Issue comments.
- Updated the required service account scopes: *write:comments* to add comments, and additionally *read:comments* and *admin:comments* for ***wiz-defend-clear-threat-comments*** to delete other authors' comments. *admin:comments* does not replace the read/write scopes. The legacy *write:threat_issue_comments* scope does not grant access to Issue comments.
- Updated the ***wiz-defend-get-threat*** and ***wiz-defend-get-threats*** commands and the fetched incidents to no longer include threat notes.
- Updated the ***wiz-defend-clear-threat-comments*** command to clear Issue comments only. Notes added through the legacy Issue Notes API that do not appear as comments in Wiz are not cleared.
- Improved implementation of the ***wiz-defend-resolve-threat*** and ***wiz-defend-reopen-threat*** commands to update the threat status and return a warning when the note cannot be added, for example when the service account lacks the *write:comments* scope.
- Fixed an issue where ***wiz-defend-set-threat-comment*** and ***wiz-defend-set-threat-in-progress*** reported success for an invalid issue ID.

#### Mappers

##### Wiz Mapper

- Updated the mapper to no longer map the **Wiz Issue Note** field, which relied on the retired Issue Notes field.

##### WizDefend Mapper

- Updated the mapper to no longer map the **Wiz Issue Note** field, which relied on the retired Issue Notes field.
