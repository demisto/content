
#### Integrations

##### Group-IB Threat Intelligence

- Updated the `compromised/breached` collection name to `compromised/breacheddb`, the name the Group-IB API uses, in *Collections to fetch*, the *collection_name* argument of ***gibti-local-search*** and behind ***gibti-get-compromised-breached-info***. The old name is refused with *Collection compromised/breached is obsolete; use compromised/breacheddb instead*, so a stale instance setting fails visibly.
- Updated the fetch of `compromised/breacheddb` to use a `seqUpdate` cursor like every other collection, starting from *Incidents first fetch* after the upgrade, and to make one incident per leak and upload for a credential found in several leaks. A breached record's ID names the credential and comes back with every leak and upload it appears in, so the duplicate cache keys on the ID, the leak and the upload time.
- Fixed an issue where every breached record became a *Low* incident. A record that carries a password is *High*, and so is one whose leak columns hold a credential or quote a secret, under every password-masking mode, so masking never hides whether a password was there.
- Updated the collections of both integrations to drop `compromised/mule`, which Group-IB superseded with `compromised/spd`. Selecting it fails with *Collection compromised/mule is obsolete; use compromised/spd instead*. The **GIB Compromised Mule** incident type, its layout, fields and classifier rule are kept so that existing incidents stay readable.
- Deprecated the ***gibti-get-compromised-mule-info*** command. It fails with an error naming ***gibti-get-compromised-spd-info***.
- Deprecated the `gibtia-` command names. The command list marks them as deprecated, and every call adds a War Room warning that names the `gibti-` replacement. ***gibtia-get-compromised-mule-info*** instead fails with an error naming ***gibti-get-compromised-spd-info***, as ***gibti-get-compromised-mule-info*** does.
- Updated the integration to use the Group-IB SDK that the Docker image bundles.
- Added the *Delay between API requests (seconds)* advanced parameter, default `1.2`, which sets the minimum delay between requests to the same collection. Raise it if the API answers HTTP 429, or set `0` to disable the delay.
- Updated the ***gibti-ip-scoring*** command to give the verdict band of the risk score in *GIBTI.Scoring.score*: 0-39 good, 40-79 suspicious and 80-100 bad, and unknown only without a risk score.
- Updated the ***ip*** and ***domain*** reputation commands to share one verdict policy. *Bad*: a risk score of 80-100. *Suspicious*: a risk score of 40-79, a listing in `ioc/primary` (the collection of indicators of compromise) at any risk score, or, for ***ip*** only, a listing in a `suspicious_ip/*` collection selected in *Collections that keep an IP at least Suspicious*. *Good*: a risk score of 0-39 without such a listing. *Unknown*: no risk score and no listing. `ioc/common`, threat reports, actor profiles, `hi/open_threats` posts and defacements do not decide. The War Room note names the collections of the records that mention the value without deciding the verdict, and it reports no data only when no collection lists or mentions the value and Group-IB has no risk score for it.
- Fixed an issue where the ***ip***, ***domain*** and ***file*** commands reported a refused key or an unreachable API as no data. A refused key (HTTP 401) now fails the command; a value for which no request of the lookup answers gets an error entry of its own; any other failed request, such as a collection the key cannot read, is named in the War Room note.
- Added the ***url*** reputation command. Group-IB scores IPv4 addresses and domains only, so the verdict comes from `ioc/primary`, read directly, and only a record that lists the URL itself counts: *Bad* when it lists the URL with a risk score of 80 or more, *Suspicious* with a lower risk score or none, otherwise *Unknown*. The URL is sent with defanged values restored and without a user name or password, and the path of a listed URL keeps its case. The collection and the threat and actor names of its records become tags, the malware families go to **Malware Family**, and, with *Create relationships* enabled, the malware families and actors become relationships; the result takes the most restrictive TLP of the matched records. *Enable reputation commands* has a new `url` option. A refused key (HTTP 401) fails the command.
- Added the *Collections that keep an IP at least Suspicious* parameter, which selects every `suspicious_ip/*` collection by default. ***ip*** returns at least *Suspicious* for an IP these collections list, whatever its risk score, tagged with the collection and without malware or actor names; the parameter does not apply to ***domain***. Clear a collection to leave the verdict to the risk score and `ioc/primary`; select only `none` so that no listing keeps an IP at least Suspicious, since an empty selection uses the default.
  - Note: A collection counts only when one of its records is the IP itself, not one that merely mentions it, and the result takes the most restrictive TLP of the listings that count.
- Added the *Suspicious IP listing recency (days)* advanced parameter, empty by default. Empty or `0` lets a `suspicious_ip/*` listing keep an IP at least *Suspicious* in ***ip*** at any age; a number of days counts only the listings Group-IB last saw (`dateLastSeen`) within that window, in every `suspicious_ip/*` collection, so that rotated proxies, relays and gateways do not stay *Suspicious*.
- Updated the lookup indicators to take the verdict of their collection: *Bad* for threat reports, `malware/cnc` C&C servers and `osi/vulnerability` CVEs, *Suspicious* for the other collections, the C&C of compromised accounts and DDoS attacks included, and the illegal score for payment details, where 80-100 is *Bad*. Group-IB's evaluation severity rates how urgent a record is, not how malicious its observables are, and does not set the verdict: a Tor exit node rated green is *Suspicious*.
- Updated the War Room output of the lookup commands. A lookup writes one table per indicator type, with its indicators and relationships, instead of one entry per indicator field holding all its values. Each nested object, such as a CVE's CPE table or affected software, is one table with a row per element instead of an entry per row. In the main table and the nested-object tables, a cell over 1,000 characters is cut with a note and a table keeps its first 200 rows, while the context keeps the whole record. The main table no longer repeats the record's indicators block, such as a CVE's description and software list. The CPE table shows each row's `update`, such as `alpha1` or `rc1`. Attributes that are empty on every row are left out of the context and the tables.
- Updated the DBotScore entries the integration writes to carry one vendor name, `GroupIBTI`, instead of `GIB TI` on the lookup command indicators.
- Fixed an issue where the indicators of the lookup commands, and reputation results without a matched record when *Ignore Source Reliability override* is enabled, had no reliability. Every DBotScore carries the instance *Source Reliability*, default `C - Fairly reliable`. With *Ignore Source Reliability override* enabled, a reputation result that `ioc/primary`, `ioc/common`, `apt/threat`, an open threat or a defacement matched takes the reliability of those collections instead.
- Updated the `compromised/account_group` lookups and incidents to extract only the C&C URL, domain and IP of each event, with the malware family and threat actor of that event as fields, tags and relationships. The C&C IP no longer carries the compromised user's ASN and location, which belong to the victim.
- Added the *IP.Address* output to ***gibti-get-compromised-account-info*** for the C&C IP of an event.
- Updated the `attacks/deface` lookups and incidents to yield only the defaced URL, as the site's domain and IP are the victim's, and the `attacks/phishing_group` ones only the phishing URLs, as the domain and hosting IP are often shared infrastructure such as a free blog host or a cloud provider's address. The removed values stay on the incidents, and phishing group and defacement incidents extract URLs only.
- Updated the phishing kit incidents to list their e-mail addresses in **GIB Related Emails** instead of **GIB Related Indicators Data**, and the threat report incidents to list the addresses of their email-message entries there. The field is extracted as **Email** indicators only, so an address's domain does not become a **Domain** indicator.
- Updated the *id* argument of ***gibti-get-suspicious-ip-vpn-info***, ***gibti-get-suspicious-ip-scanner-info*** and ***gibti-get-malware-malware-info***, and the *ip*, *domain* and *file* arguments of ***ip***, ***domain*** and ***file***, to be required, since the commands fail without them.
- Fixed an issue where `osi/git_repository` incidents and ***gibti-get-osi-git-leak-info*** created a File indicator for every revision hash of the leaked files and an Email indicator for every committer. Git leaks create no indicators.
- Updated the lookup commands and **GIB Related Indicators Data** to yield no indicators from `compromised/bank_card_group` and `compromised/masked_card` records. Their `cnc` block is the shop the card was offered in, not attacker infrastructure, and stays in the incident's events table.
- Fixed an issue where a threat report file without an MD5 produced no indicator. In the lookup commands and **GIB Related Indicators Data**, a file is keyed by its SHA-256, else its SHA-1, else its MD5, else its SHA-512.
- Fixed an issue where **GIB Related Indicators Data** held the record's whole indicators block, so incidents also extracted its attributes: hosting providers, the links of a CVE description, the defaced site's domain and IP, the names of a threat report's files and every hash of a file as its own File indicator. The field lists only the record's observables, one per line, the values the lookup commands turn into indicators.
- Fixed an issue where Nessus, Red Hat, Microsoft, Oracle and WordPress advisories in `osi/vulnerability`, which carry their own IDs, such as Nessus plugin IDs or `MS:` IDs, became CVE indicators. Only a CVE ID becomes a CVE indicator.
- Updated the threat report incidents to no longer fill **GIB Is Tailored**, and ***gibti-get-threat-info*** to write no *isTailored* under *GIBTI.GIBCybercriminalThreatReport* or *GIBTI.Nation-StateCybercriminalsThreatReport*. To find the reports fetched through your hunting rules, use **GIB Fetched With Hunting Rules**.
- Fixed an issue where incidents of one address overwrote each other. Every `suspicious_ip/*` collection uses the address as the record ID, and `suspicious_ip/open_proxy` can list one address several times, each listing with its port. Each port of an open proxy is its own incident, named `Suspicious IP Open Proxy: <address>:<port>`. **GIBTIIncidentUpdateAllTypes** and **GIBTIIncidentUpdate** update only an open incident of the same incident type, **GIBTIIncidentUpdateIncludingClosed** a closed one too, and for an open proxy only one with the same **GIB Proxy Port**. *Skip updated incidents (prevent duplicates)* remembers a record by its collection and ID, an open proxy by its address and port, and a breached record by its ID, leak name and upload time.
- Note: Upgrading keeps the duplicate cache while *Skip updated incidents (prevent duplicates)* is enabled and *Deduplication lookback (days)* is above 0 (a fetch with either one off empties the cache), and a record ID an earlier version remembered still hides its record, except a breached record, now remembered with its leak and upload time, which can arrive once more. A remembered IP address is kept only when the instance last fetched exactly one `suspicious_ip/*` collection and that collection is not `suspicious_ip/open_proxy`. It then hides that collection's record of it. Any other remembered address is dropped so that it cannot hide another collection's record or another port, and the record it named can arrive once more. Where **GIB Rule All Types** runs, the rule merges the record into the open incident of the same type; without the rule, which the pack does not install on Cortex XSIAM and the Cortex platform, the record arrives as a new incident or alert.
- Fixed an issue where the ***ip*** command wrote an IPv6 address under *IP*. It writes it under *IPv6*, with *IPv6.Address* and the keys of *IP*, as the lookup commands do.
- Fixed an issue where phishing group incidents were named after the brand alone, which can be a placeholder such as `Not specified`. They are named after the phishing domain, followed by the impersonated brand in parentheses when the record names one other than the domain, and ***gibti-local-search*** shows the domain too. Phishing group indicators no longer get such placeholders as tags.
- Updated the fetch to skip a phishing group that Group-IB flags as a false positive or allow-listed instead of making it an incident. An incident built from such a record lists nothing in **GIB Related Indicators Data**, and ***gibti-get-phishing-group-info*** returns no indicator, object or relationship for such a group and names the flag that withdrew it.
- Updated the help of *Skip updated incidents (prevent duplicates)*. The pack does not install the pre-processing rule **GIB Rule All Types** on Cortex XSIAM and the Cortex platform, so on those platforms nothing merges a record that Group-IB sends again after an update, and each update arrives as a new alert. Enable the setting on those platforms: it skips a record already fetched, so the update does not arrive. Where **GIB Rule All Types** runs, leave it disabled so that the rule updates the existing incidents, and enable it if you do not use the rule.
- Added the *Pass flagged phishing groups to the pre-processing rule* parameter, off by default. When it is off, a flagged group is dropped at fetch and never opens an incident, and an incident opened before Group-IB set the flag never shows it. When it is on, flagged groups go to **GIB Rule All Types**, which sets **GIB False Positive** or **GIB Allow Listed** on the group's open incident and drops the record, as it drops a flagged group without an open incident. While the duplicate cache is on (*Skip updated incidents (prevent duplicates)* enabled and *Deduplication lookback (days)* above 0), only a group the integration already made an incident of is handed on.
  - Note: Turn the parameter on only while **GIB Rule All Types** runs; the pack does not install that rule on Cortex XSIAM and the Cortex platform. Without the rule, every flagged group handed on opens an incident of its own, a second one when the group already has an incident.
- Updated the lookup, **GIB Related Indicators Data** and **GIBTIEnrichIncidentIndicators** to make a Bitcoin wallet of `compromised/spd` the indicator `bitcoin:<address>`, one indicator per wallet. A Bitcoin address is a valid base58check address starting with `1` or `3`, or a `bc1` address. Cortex XSOAR's own extraction gives a base58check wallet the same value, and **GIBTIEnrichIncidentIndicators** creates a `bc1` wallet. Wallets of other chains keep the address as Group-IB gives it, and only **GIBTIEnrichIncidentIndicators** creates them: Cortex XSOAR's extraction does not recognize them, so **GIB Related Indicators Data** does not list them. A payment identifier of ***gibti-get-compromised-spd-info*** whose record is a crypto wallet is a **Cryptocurrency Address** indicator.
- Updated the *Incidents first fetch* parameter so that changing it restarts every selected collection from the new date. The stored `seqUpdate` cursors are dropped when the value differs from the one the last fetch ran with.
  - Note: An instance upgraded from an older version records *Incidents first fetch* and *Hunting Rules* on its first fetch on 4.0.0 and keeps its cursors until then, so a change made before that fetch does not restart the collections.
- Fixed an issue where records of `suspicious_ip/*`, `compromised/spd`, `malware/cnc` and `osi/public_leak` that share a cursor position were skipped where a page ended. The fetch now reads such records across page edges, and stores the digests of the last position it read with its cursor, so an unchanged record is not delivered twice.
- Fixed an issue where the lookup commands reported Group-IB's placeholders of an unknown date (`0001-01-01`, `1976-01-01`) as dates.
- Fixed an issue where a collection without a start cursor was read from its oldest record. Each collection starts at the Group-IB cursor for the *Incidents first fetch* date, and `attacks/ddos` and `attacks/phishing_kit` start from the date itself when no cursor is available. Any other collection without a cursor for that date is not read yet: the instance health names it, the cursor is requested again on the next fetch, and the other collections are fetched. If a collection keeps waiting, set a later date; changing the date restarts every selected collection.
- Added a step to the instance **Test** that links **GIB Rule All Types** and **GIB Rule** to their scripts when the rule has no script selected. If the link cannot be saved, the integration log names the rule; select the script in the rule.
- Updated the git leak incidents to take as severity the worst grade of the repository and its matched files: red is *High*, orange *Medium*, yellow and green *Low*, and gray rates nothing. The files table and the new *GIBTI.GitLeak.files.severity* output show each file's own grade.
- Updated the Malware incidents to take their severity from the profile's threat level, *High*, *Medium* or *Low*, and the Malware C&C incidents, whose `malware/cnc` records carry no Group-IB evaluation, to *High*.
- Updated the Malware incidents to show the threat actors in **GIB Threat Actor Name** and **GIB Threat Actor ID** as comma-separated text instead of the JSON of a list.
- Added the *Lookup timeout (seconds)* advanced parameter, default `20`, which limits how long one value of ***ip***, ***domain***, ***file*** and ***url*** waits for its Group-IB requests. A request that has not answered by then is left out, and the War Room note names it. A verdict is then set only if no missing answer could have raised it. Without a verdict, the indicator keeps the one it has. A ***url*** sends one request, so a ***url*** without an answer gets an error entry. A list of IPs or domains first waits up to the same time for its risk scores. `0` waits without a limit.
- Added the *Parallel requests per lookup* advanced parameter, default `4`, the number of Group-IB requests one value of a reputation command sends at once.
- Added the *Use the Group-IB global search* advanced parameter, off by default. Enabled, ***ip***, ***domain*** and ***file*** also list the other collections that mention the value; they do not decide the verdict.
- Improved implementation of the reputation commands, which read their collections, the risk score and the WHOIS record directly, up to *Parallel requests per lookup* at a time, instead of through the Group-IB global search. The record of an IP in a `suspicious_ip/*` collection is read by its ID, the IP itself, instead of a search.
- Improved implementation of ***ip***, ***domain*** and ***gibti-ip-scoring***, which ask for the risk scores of a list of values in one request per 100 values instead of one request per value.
- Added the ***gibti-ip-whois*** and ***gibti-domain-whois*** commands, which return the registry record of an IP address or a domain from the Group-IB Graph WHOIS: for an IP the address range, registry, network name, holder organization, ASN, AS owner and abuse contact; for a domain the registrar and its abuse contact, the registrant, statuses, dates and name servers, a subdomain answered with its registered domain. *history=true* adds up to *history_limit* earlier records (default 10).
- Added the *Add WHOIS to ip and domain* advanced parameter, on by default, which writes the ASN, holder organization, AS owner and abuse contact of an IP, and the registrar and its abuse contact, the registrant, statuses, dates and name servers of a domain, to the indicators of ***ip*** and ***domain***. *Domain.CreationDate* and *Domain.UpdatedDate* are written as `03 Feb 2001 04:05:06 UTC`, the form the Domain indicator type reads into *Creation Date* and *Updated Date*; *Domain.WHOIS.CreationDate* and *Domain.WHOIS.UpdatedDate* keep the ISO form.
- Added the *WHOIS personal data* advanced parameter, `Show` by default, whose `Drop` leaves out a registrant's name and e-mail address.
- Added the *Collection tags at every verdict* advanced parameter, on by default, which tags a *Good* or *Unknown* reputation result with the collections that list or mention the value, without their malware or actor names, and never with a collection of *Collections that keep an IP at least Suspicious*.
- Updated the ***file*** command to take its verdict from `ioc/common` and `ioc/primary`: a hash that `ioc/common` lists, or that `ioc/primary` lists with a risk score of 80 or more, is *Bad*, and a hash only `ioc/primary` lists, with a lower risk score or none, is *Suspicious*. Its indicator carries one hash of each other kind found in the records of both collections and their most restrictive TLP, an `ioc/common` record counting as AMBER.
- Added the *FirstSeenBySource* and *LastSeenBySource* outputs to ***ip***, ***domain***, ***file*** and ***url***: the earliest first and the latest last sighting of the Group-IB records that list or mention the value.
- Added the *Publications* outputs to ***ip*** and ***domain***: the `apt/threat` reports and `hi/open_threats` posts of a result the risk score makes *Suspicious* or *Bad*, newest first.
- Fixed an issue where ***ip*** wrote the description of the network as the owner of the autonomous system, a phone of the network or a placeholder number as the abuse phone, and the country where the range is registered as the country of the address. ***ip*** now takes the holder organization, the ASN, the AS owner and the abuse e-mail address and phone from the registry objects, each from the newest WHOIS record that has it.
- Updated the ***domain*** command to write, with *Add WHOIS to ip and domain* on, the registrar and its abuse contact, the registrant, the statuses, dates and name servers of the domain to its indicator, including *Domain.Whois.Registrar*, the lowercase keys under *Domain.Registrant* and *Domain.Admin.Organization*, the keys the Domain indicator type reads its Registrar, Registrant and Organization fields from.
- Added the *Look up internal and reserved IP addresses* advanced parameter, off by default, also on instances upgraded from an earlier version. ***ip***, ***gibti-ip-whois*** and ***gibti-ip-scoring*** answer a private, loopback, link-local, shared or reserved address, the documentation ranges included, with a note and ask Group-IB nothing unless the parameter is on.
- Updated the ***ip***, ***domain*** and ***file*** commands to report a partial lookup when a request that decides the verdict fails or does not answer within *Lookup timeout (seconds)*: *GIBTI.Reputation.partial* is true, *GIBTI.Reputation.failedSources* names the requests that failed or did not answer, and a verdict is set only if no missing answer could have raised it. A missing risk score or `ioc/common`, or the `ioc/primary` of a file, could make it *Bad*, so only a *Bad* verdict is set; a missing `ioc/primary` of an IP or domain or a missing `suspicious_ip/*` collection could make it *Suspicious*, so a *Suspicious* or *Bad* verdict is set and a lower one is not. Without a verdict, the indicator keeps the one it has. HTTP 403 (the key has no access) and HTTP 404 (no record) do not make the result partial, and the verdict comes from the other requests.
- Added the *GIBTI.Reputation* outputs to ***ip***, ***domain***, ***file*** and ***url***: the value, its verdict, risk score and collections, the number of records per collection that list or mention the value on the one page the lookup reads, with their sighting dates, and whether the lookup was complete. A *Bad* result also carries *Malicious.Vendor* and *Malicious.Description*.
- Updated the ***ip*** and ***domain*** commands to refang the value first; ***domain*** also lowercases it and drops a final dot. ***ip*** sends no IPv6 address to `scoring/ip`, which scores IPv4 addresses only.
- Added the *Mask passwords and leaked secrets* parameter, default `Off`, which masks passwords and leaked secrets in incident fields, the lookup commands and ***gibti-local-search***. `Partial` keeps the first half of each password or secret followed by `****`. `Full` drops the passwords and credential columns, puts `[withheld]` in place of other secrets and withholds the raw text of a public leak.
  - Note: The parameter covers the passwords of `compromised/account_group` and `compromised/breacheddb` records (**GIB Password**, **GIB Passwords**) and the columns of a breached record's leak in **GIB Breach Record Details**, at any depth, whose name says they hold a password, secret, salt, token, session ID, password hash or secret key (`user_pass`, `accessToken`, `sessionId`, `apiKey`, `passwordHash`, `md5`). It also covers the extracted values and raw text of `osi/public_leak` records. In these records and in dark web posts it masks secrets written after a credential name, the passwords of e-mail:password pairs, url:login:password lines and URLs, Authorization headers, Bearer and Basic credentials, crypt hashes, the LM and NT hashes of NTLM dump lines, private keys and GitHub, GitLab, Slack and Stripe tokens. It also masks every other copy of a password or secret the record names or a text quotes, where the copy stands apart from other letters and digits: from six characters, or from four in a sentence for a value the record names.
  - Note: A login, a parsed login domain, a service domain or a breached record's e-mail address or e-mail domain stays as it is when the password is part of its name (`sample@example.com`, the user of `CORP\sample`) or the whole of it, so the incident keeps naming its account: a password equal to the login stays readable there under Partial and Full. In those fields, a `login:password`, a URL, a password in the domain of a `DOMAIN\user` login or a password written beside a login is masked. A hash of anything else (`emailHash`), a passport number and a column that dates a credential, names its type or describes it (`passwordChangedAt`, `hashType`, `passwordLength`) keep their value, as does a flag, a placeholder or an empty value in a credential column.
- Added the *Mask card data* parameter, off by default. When it is on, a `compromised/bank_card_group` record keeps the first six and last four digits of its card number, in the incident name too. It loses its CVV and shows `[redacted]` for the cardholder's name and phone before it reaches incidents, ***gibti-get-compromised-card-group-info*** or ***gibti-local-search***. When it is on, a `compromised/masked_card` record, whose card number arrives masked and whose owner details arrive in plaintext, shows `[redacted]` for the owner's name, address, birthday, e-mail, phone, city, ZIP code, passport and tax number in incidents, ***gibti-get-compromised-masked-card-info*** and ***gibti-local-search***. The owner's state and country stay.
- You can now pass a list of IDs to ***gibti-get-threat-info*** and ***gibti-get-threat-actor-info***, and both commands now choose the collection, `hi/*` or `apt/*`, from *isAPT*. Each ID is read from the collection that *isAPT* selects and, when that collection does not have it, from the other one, since a malware profile lists several actors without an APT flag.
  - Added a War Room note that lists the IDs neither collection publishes, such as a defacer Group-IB tracks only in `attacks/deface` or an unpublished actor profile or report, instead of failing the command. Such an ID is reported as not published when the collection's update feed does not list it either. An ID that both collections refuse fails the command when no other ID was read, and is named in the note otherwise; an ID one collection does not publish and the other refuses, as for a key without access to the APT collections, is reported as not published, with the refusal in the same note.
- Updated the ***gibti-get-threat-info*** and ***gibti-get-threat-actor-info*** commands to write their records under *GIBTI.GIBCybercriminalThreatReport*, *GIBTI.Nation-StateCybercriminalsThreatReport*, *GIBTI.GIBCybercriminalThreatActorProfile* or *GIBTI.Nation-StateCybercriminalsThreatActorProfile*, by the collection each record comes from, instead of the *GIBTI* root.
- Added the *Create relationships* parameter, on by default. The lookup commands, and the *Suspicious* or *Bad* results of the reputation commands, relate their indicators to the **Malware** objects their records name with `indicator-of` and to the **Threat Actor** objects with `related-to`. No relationship is made for a result that only *Collections that keep an IP at least Suspicious* made Suspicious, or to the defacer of an `attacks/deface` record. Disable the parameter to keep the commands to plain observables. The feed integration and the new **GIBTIEnrichIncidentIndicators** automation create the objects the relationships point to.
- Updated the reputation commands to enrich a *Suspicious* or *Bad* indicator with its matched records: their collections, threat names and threat actors as tags, their malware families in **Malware Family**, and their most restrictive TLP. ***ip*** and ***domain*** take them from every matched record when the risk score decides, from the `ioc/primary` records when `ioc/primary` makes the result *Suspicious*, and only the collection tag and its TLP from a `suspicious_ip/*` listing. A *Good* or *Unknown* result gets none of them, apart from the collection tags of *Collection tags at every verdict*. Actor profiles are not read, as the domains a profile lists are the actor's victims. A defacement counts only when it defaces the IP or domain itself (its target domain, the host of the defaced URL or its target IP), and adds the `attacks/deface` tag and its TLP but never the defacer, since the defaced site is a victim, not the actor's infrastructure.
- Added the ***gibti-domain-scoring*** command, the domain counterpart of ***gibti-ip-scoring***, on `scoring/domain`. It reads the domain score on the same scale, a list in one request per 100 values, and gives an IP address a War Room note without a request. Both scoring commands write the risk score and its verdict band to *GIBTI.Scoring* and set no verdict on the indicator, which the reputation commands set. A refused key (HTTP 401 or 403) fails the command; any other failed request is the error entry of its value. An empty answer gives no score and the unknown band; a score of 0, which Group-IB gives a value it has no data on, is in the good band.
- Improved implementation of ***gibti-ip-scoring***, which sends only IPv4 addresses and gives any other value a War Room note without a request.
- Added the ***gibti-cve-scoring*** command, which scores CVEs from `osi/vulnerability`. It combines whether an exploit is available, whether the CVE is seen in the wild, EPSS and CVSS with Group-IB's severity into a DBotScore by rules the README lists, and a CVE that Group-IB has a record of is never *Good*. The command returns the DBotScore with the CVE indicator, which carries the CVSS score and vector, dates, description and TLP, and writes the full detail to *GIBTI.CVEScoring*. - Reads the record on the instance that fetched the incident (*using*) or on the only active instance, and the *instance* argument overrides both. With several active instances and none of them the one that fetched the incident, the command runs on every instance.
- A **GIB Data Breach** incident joins several IDs in its **GIB ID** with `, `, and the script reads the record by the first. A phishing group that Group-IB flags as a false positive or allow-listed gives no indicator and no object.
- Creates **IPv6** indicators, files known only by their SHA-512, and **Email** indicators with the tags and TLP of their record, so an e-mail address from a TLP:RED report keeps its sharing restriction. Entries of a defacement lookup stay excluded from extraction, so the defaced site's host never becomes a **Domain** indicator.
- Enriches the indicators of **GIB Open Threat** incidents and reports that a dark web listing or post (**GIB Compromised Access**, **GIB Darkweb Telegram**, **GIB Darkweb Discord**, **GIB Darkweb Forum**) carries none.

##### New: GIBTICreateThreatIntelReport

- Creates a Threat Intel Report from a Group-IB record, with the out-of-the-box report type that fits the collection: **Campaign** for threat reports (`hi/threat`, `apt/threat`), **Threat Actor** for actor profiles (`hi/threat_actor`, `apt/threat_actor`), **Malware** for `malware/malware` and **Vulnerability** for `osi/vulnerability`. It needs no arguments inside an incident of these collections and supports *dry_run*.
- Reads the record with the matching `gibti-get-*-info` command on the instance that fetched the incident (*using*) or on the only active instance, and the *instance* argument overrides both. With several active instances and none of them the one that fetched the incident, the command runs on every instance.
- Uses the built-in ***createThreatIntelReport*** command for the report and ***setThreatIntelReport*** for its body, description, source and threat actor.
- Writes the record's description, short description and extended description to the body as the lookup returns them: as text, without the embedded figures, which need the API credentials. Each paragraph, list item and table cell of the record becomes a body paragraph.
- The *Indicators* table lists the report's IPv4, domain, URL and file entries: one row per IP of a network entry, defanged values restored, placeholders skipped, and one hash per file (SHA-256, else SHA-1, else MD5).

##### New: Group-IB TI - Create Threat Intel Report

- Creates a Threat Intel Report through **GIBTICreateThreatIntelReport** for the six Group-IB incident types that map to a report type (threat reports, actor profiles, malware, vulnerabilities). Its inputs *ReportType* and *DryRun* are optional; with *ReportType* empty, the collection sets the report type. Since the default playbook of every Group-IB incident type is **Incident Postprocessing - Group-IB Threat Intelligence & Attribution**, it ships attached to none: attach it, call it as a sub-playbook, or run the automation by hand.

##### New: Group-IB TI - Compromised Account Response

- Responds to a **GIB Compromised Account Group** incident: checks that the login belongs to one of your domains, enriches the indicators and looks the account up in your directory (**Account Enrichment - Generic v2.1**). When a directory knows the account, it searches the SIEM for failed logins and lists the user's devices. It then resets the password and ends the sessions and disables the account, each automatically or after an analyst's decision as the inputs say, and opens a ticket for the compromised device when *CreateTicket* is `True` and the stealer log names the device. The remediation runs through the generic sub-playbooks, which use the directory, SIEM, EDR and ticketing integrations enabled on your tenant. **Containment Plan - Clear User Sessions**, **Eradication Plan - Reset Password** and **Ticket Management - Generic** ship only for Cortex XSIAM and the Cortex platform; on a tenant without them, the steps that call them are skipped.

##### New: Group-IB TI - Malware C2 Response

- Responds to a **GIB Malware CNC** incident: creates the C&C's indicators with Group-IB's verdict, asks the ***domain*** and ***url*** reputation commands for their context, hunts for them in the SIEM and EDR (**Threat Hunting - Generic**), offers to isolate the hosts that talked to the C&C (**Isolate Endpoint - Generic V2**), asks the analyst to open an incident per detected host or user, and blocks the indicators Group-IB scores *Suspicious* or *Bad* on the perimeter (**Block Indicators - Generic v3**).

##### New: Group-IB TI - Vulnerability Triage

- Triages a **GIB OSI Vulnerability** incident. For a CVE record it scores the CVE with ***gibti-cve-scoring***, enriches it (**CVE Enrichment - Generic v2**), searches the scanner for the hosts that carry it when *ScannerConnected* is `True` (**Search Endpoint by CVE - Generic**) and, when *CreateTicket* allows it, opens a patch ticket (**Ticket Management - Generic**) whose urgency follows the exploit evidence and the EPSS and CVSS thresholds. An incident without a vulnerable host is closed as not applicable only when the inputs allow it and a scanner is connected. Records that are not CVEs are left to the analyst. **Ticket Management - Generic** ships only for Cortex XSIAM and the Cortex platform; on a tenant without it, the steps that call it are skipped.

##### New: Group-IB TI - Phishing Takedown

- Responds to a **GIB Attacks Phishing Group** incident: creates the phishing URL indicators and blocks the URLs (**Block URL - Generic v2**). When *BlockDomain* is `True` (default `False`, since a phishing domain is often shared hosting), it also blocks the domain through **Block Domain - Generic v2**, which asks no one. It searches and deletes the e-mails received in the last 7 days whose body names the domain when *SearchAndDeleteIntegration* is MS Graph, and sends the takedown request to the registrar and the hosting provider by mail or hands it to the analyst. It then polls Group-IB through ***gibti-get-phishing-group-info*** until the group is marked blocked, reads the group once more and closes the incident when the inputs allow it.

##### New: Group-IB TI - Leaked Credentials and Secrets

- Responds to the **GIB Data Breach**, **GIB OSI Git Leak** and **GIB OSI Public Leak** incidents: resets the passwords and ends the sessions of breached accounts of your domains, rotates the cloud credentials a public repository exposed (**Cloud Credentials Rotation - Generic**), notifies the committers and opens a ticket for the developers, each as the inputs allow, and routes the payment card data of a public leak to the fraud team. **Containment Plan - Clear User Sessions**, **Eradication Plan - Reset Password** and **Ticket Management - Generic** ship only for Cortex XSIAM and the Cortex platform; on a tenant without them, the steps that call them are skipped.
